- **Kind:** code
- **Task:** none

## 2026-11-03 · fix(cli): launcher version + sync config pin
- **Kind:** code
- **Task:** none
- **Bug:** BUG-0019
- **Why:** the repo's own `.codictator/config.json` still pinned `codictator: "0.0.0"` after the 0.1.2 release, so every `verify` failed closed with CDX-E102 (SPEC §4.2.1 step 2, EC-11); syncing the pin alone is not enough because the launcher called `engine.main(args, cwd)` with no version, so hook-path validation compared the pin against the `"0.0.0"` placeholder while the direct CLI entry compared against the installed manifest version — no single pin satisfies both
- **What went wrong:** resolving the placeholder inside `main()` would re-resolve per call and break every source-run test pinning `"0.0.0"`, so the version read stays in the launcher (`installedEngineVersion` reads the resolved engine's own manifest) with a two-argument fallback when the manifest is unreadable or version-less; the generated launcher uses `const` (never `var`, per the ts/lint gate) and the template module carries a `LauncherText` alias so the single-definition export stays referenced in-module; `codictator regen` in a worktree also rewrote the scheduled-workflow cron because `scheduleCronFor` hashes the checkout directory basename, so that hunk was reverted and `manifest.json` rebuilt through the shipped `buildManifest` code path instead
- **Trade-offs:** no BUGS registry row for the pin itself (stale repo data, not a code defect); the checked-in `run.mjs` is regenerated from `LAUNCHER_TEXT` in the same commit
- **Lessons:** entry-point version resolution belongs where the process boundary is crossed (the bin entry for direct invocation, the launcher for imported invocation); never commit a worktree regen verbatim — diff it against the committed guardrails and drop basename-derived churn
- **Docs:** docs/SPEC/04-19-CLI.md
