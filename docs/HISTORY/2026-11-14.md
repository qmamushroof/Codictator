## 2026-11-14 · docs(spec): specify write confinement of code-shaped targets and unparseable shell sources
- **Kind:** docs
- **Task:** T-0047
- **Why:** SPEC §4.7.3 was silent on a write target holding code characters and on a shell source that cannot be parsed, so BUG-0100 could not be fixed against a stated rule; this states that a target is judged as a path or fails closed, that only a code-shaped write: line in a source file is skipped, and that an unparseable shell source blocks with CDX-E306.
- **What went wrong:** nothing abandoned; the open bug row was filed in this change so the fix has a row to flip.
- **Trade-offs:** a write: line in a non-source file, such as prose in a doc, is now judged as a path and can block or fail closed as unresolvable, which is accepted to keep the rule fail-closed.
- **Lessons:** a skip that applies to source files must not be implemented as a character filter on every file.
- **Docs:** docs/SPEC/04-07-SECURITY-GUARDS.md, docs/BUGS/2026.md

## 2026-11-14 · fix(kernel): parse compound commands, process substitution and heredocs in the shell analyser
- **Kind:** code
- **Task:** T-0046
- **Bug:** BUG-0099
- **Why:** once core/dangerous-shell judged whole workflow run bodies, this repo's own codictator.yml and release.yml reported CDX-E306 and test-heavy.yml reported a pipe into a shell; four defects caused it: a leading keyword such as if re-parsed its decoded words joined by spaces, which lost quoting and failed on a quoted expression with double braces, a process substitution as a redirection target gave an empty target, every heredoc body was judged as shell for any command, and every pipe into node or python was blocked even when an inline program ran. SPEC §4.7.2 now states these rules (T-0045); the keyword is dropped and the words after it are judged as written, the process substitution is descended, a heredoc or here-string body is judged only when a shell receives it, and a pipe into an interpreter with an inline program is allowed unless a download feeds it.
- **What went wrong:** the bug row blamed heredocs, arrays and if blocks as such, but they already parsed; reproducing over the real workflows found the four causes. Review of the SPEC change showed the inline-program exemption would let a download be evaluated, so the download check now fires for a download anywhere earlier in the pipeline, which also closes curl piped through tee into a shell; review then found that a shell given an inline program that is itself a bare interpreter, such as sh -c sh, still executes the piped data, so that program is parsed and the exemption is withheld.
- **Trade-offs:** array elements are still judged as commands, so a word list that looks like a dangerous command is flagged; the inline-program flags are a fixed list, so a combined flag such as bash -ec stays blocked; kernel-shell.test.ts asserted the old keyword descent and was changed to assert the dropped keyword, an integrity exception for the reviewer.
- **Lessons:** re-parsing decoded words as text drops quoting, so a construct that wraps a command must be stripped on the word list; run a new parser rule over the repo's own workflows before trusting its unit tests.
- **Docs:** docs/BUGS/2026.md

## 2026-11-14 · fix(packs): judge the body of a workflow run block scalar
- **Kind:** code
- **Task:** T-0043
- **Bug:** BUG-0096
- **Why:** extractShellSources treated run: as a one-line key, so a step written as a block scalar yielded only its indicator character and its body, which holds the real shell, never reached the analyser, and a list-item step written with a dash was not read at all; the extractor now reads the key past list dashes, recognises the literal and folded indicators with their chomping and indent marks, and returns the indented body as one source, so a curl-pipe-sh or a recursive delete on any body line blocks.
- **What went wrong:** the first run of the new tests showed the dash form was skipped too, so the fix covers both gaps under this bug, and review then found quoted values, anchored or tagged indicators, quoted or spaced keys, flow mappings, plain multi-line scalars and a dash-tab separator unread, all now read or failed closed; the extractor moved into shell-sources.ts first so shell-analyse.ts stays under the size limit, with no behaviour change in that step.
- **Trade-offs:** a folded block is joined with spaces and judged as one command, which matches what the shell receives; quoted values are decoded (doubled single quote, the common double-quote escapes) before analysis and a value that cannot be decoded, a quoted value that does not close on its line and a flow mapping holding a run key fail closed as unparseable instead of being skipped; the key is read past list dashes, anchors, tags, a quoted key and a space before the colon, and a plain multi-line scalar is read as one folded command outside source files; a block scalar with an explicit indent digit may put its first line deeper than a later one, so the body is dedented by at most the shallowest line and, in a folded block, a more-indented line keeps its own line as YAML does instead of folding into the one before it; continuation lines indented past the key fold into a plain scalar, a full-line comment inside a plain body is dropped while a comment inside a block body stays shell, and an empty run key followed by a `key:` entry is a mapping and not read; write-confinement does not yet skip the lone-quote sentinel an unreadable run value emits, which belongs to BUG-0097; a run key written in a way not listed (an explicit question-mark key, a multi-document stream split mid-step) is still unread. Judging whole bodies also exposes shell the analyser cannot parse: this repo's own codictator.yml and release.yml now report unparseable (heredoc, bash array, if blocks) and test-heavy.yml reports a pipe into a shell, a false positive because the piped node program only reads its input as data; a staged edit of those three workflows therefore blocks at the local gate until BUG-0099, filed open, is fixed; a live agent write is not affected because the hook scope carries no disk files for this rule.
- **Lessons:** a YAML key that carries code needs the block forms and list dashes handled where the text is extracted, not in each rule that judges it.
- **Docs:** docs/BUGS/2026.md

## 2026-11-14 · fix(packs): ignore write: and run: object syntax in source files
- **Kind:** code
- **Task:** T-0042
- **Bug:** BUG-0094
- **Why:** both extractors took the text after a leading marker word as a target or a command, so an object property opening a multi-line arrow, a call-shaped line or a parameter-named call in a source file read as an unresolvable write target (core/write-confinement) or an unparseable shell command (core/dangerous-shell); one shared shape test now drops a bare opener, an arrow fragment, a trailing opener or comma and an identifier call before either rule judges it.
- **What went wrong:** the shared fake filesystem resolves every path, so a plain unit test could not reproduce the defect and the tests use a double that refuses unseeded paths, as a real filesystem does; the pre-commit duplication scan then flagged the two resolvers' shared preamble, so both now build through plainEnforcer in plain-enforcer.ts, which keeps the one-argument check shape their tests call; the first cut skipped code-shaped lines in every file, which let real workflow shell such as a trailing-comma curl-pipe-sh through, so review narrowed it to source files and three shapes and added tests that pin each bypass as still blocking; the dangerous-shell half was found only when the new blanker helper's own parameter list, written as a run: ( property, tripped the rule during BUG-0089.
- **Trade-offs:** the skip applies only in TypeScript, JavaScript and Python source files and only to three shapes: a bare opener, an arrow-function head (a parameter list of identifier characters, commas, spaces and `= . : ? [ ]`, or one identifier, optionally async, then `=>`), and a member call written with no space before its paren and holding no pipe, redirect, brace, command substitution or inner semicolon; workflow YAML, scripts, markdown and extension-less files are always judged, so a real `run:` or `write:` line there blocks whatever it ends with; the live-hook tool-input paths and shell commands are not filtered.
- **Lessons:** a marker word that doubles as an object key needs the code-shape test at the extractor, not per rule; the fake filesystem resolves every path, so regressions that depend on resolution need a strict double.
- **Docs:** docs/BUGS/2026.md

## 2026-11-14 · fix(packs): skip regex literals when blanking code
- **Kind:** code
- **Task:** T-0040
- **Bug:** BUG-0091
- **Why:** blankCode had no regex-literal mode, so a quote inside a regex literal such as a match pattern holding a double quote opened a string state that blanked real code up to the next quote, and ts/lint's unused-binding check, which counts uses over that blanked text, reported a binding unused when its only use came later; both blankers (the shared pack one and the typescript pack's own lex.ts) now step over a regex literal found by one kernel helper, regexLiteralEnd, that starts after an operator, an opener or a value keyword and closes on the same line, blanking its body.
