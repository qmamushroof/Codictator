## 2026-11-14 · docs: spec the proposedContentWhole field
- **Kind:** docs
- **Task:** T-0037
- **Why:** an L1 write carries proposed content that is either a whole file or an edit fragment, and a rule judging a whole document (dependency manifests, history append-only) misreads a fragment as the file; SPEC §4.3.2 and §7.8 now define `tool.proposedContentWhole`, true only for the whole-file input keys, and say which rules judge a fragment.
- **What went wrong:** nothing abandoned; the same wording was first proposed in a closed PR and is recreated here on the current SPEC.
- **Trade-offs:** the whole-file keys are a closed list, so an unknown content key reads as a fragment and a whole-document rule skips it rather than guessing.
- **Lessons:** a field the adapters set and the rules read has to be named in §7.8 before the code that uses it lands.
- **Docs:** docs/SPEC/04-03-ENGINE.md, docs/SPEC/07-FILES-AND-FORMATS.md

## 2026-11-14 · fix(cli): install-hooks writes executable hooks
- **Kind:** code
- **Task:** T-0036
- **Bug:** BUG-0093
- **Why:** SPEC §4.14.4 mandates mode 755 for the generated hooks and §9.2 allows executable git hooks, but writeHookFiles wrote through Fs.write, whose atomic write creates files 0666, so .githooks/* landed 0644 and git silently skipped them under core.hooksPath on POSIX; Fs.write now takes an optional mode and the hooks are written with the plan's 755.
- **What went wrong:** the first cut pushed guardrail.ts and fs.ts over the 300-line limit, so the hook writing moved to cli/hook-files.ts; core/write-confinement misread a multi-line `write: (` arrow and a parameter named `fs` as write targets, so the wrapper uses inferred parameter types and the helper names its Fs `files`.
- **Trade-offs:** the POSIX-only regression and acceptance tests were never run on the Windows authoring machine, so Linux and macOS CI are their first run; the mode is a third optional Fs.write argument rather than a separate port method.
- **Lessons:** a mode set at creation is subject to the umask, so 755 may land as 700 under a strict umask, which still runs; the recording-Fs unit test is the only platform-neutral proof of the mode.
- **Docs:** docs/BUGS/2026.md

## 2026-11-14 · fix(cli): judge only the branch's own commits at pre-push
- **Kind:** code
- **Task:** T-0035
- **Bug:** BUG-0092
- **Why:** SPEC §4.3.2 now judges only the branch's own commits at pre-push, but runPrePush diffed @{push} against HEAD, so after a rebase and force-push the diff held every commit already merged into the default branch; the diff base is now the first parent of the oldest commit reachable from HEAD but from neither @{push} nor the default branch's remote ref, read from refs/remotes/origin/HEAD.
- **What went wrong:** nothing abandoned; the acceptance test runs the hook entry directly because installed hooks are not executable on POSIX (BUG-0093), so a real git push would pass vacuously there.
- **Trade-offs:** an unreadable origin/HEAD, a root commit or a merge in range falls back to the wider @{push} base, so the gate is stricter, never looser, on those inputs.
- **Lessons:** the range and its fallbacks are covered by the unit file; a scenario builder in tests/support/prepush-scenario.ts is the one place that builds the rebased-branch repo.
- **Docs:** docs/BUGS/2026.md

## 2026-11-14 · docs: judge only the branch's own commits at pre-push
- **Kind:** docs
- **Task:** T-0034
- **Why:** SPEC §4.3.2 said pre-push judges `@{push}..HEAD`, but after a branch is rebased onto the default branch and force-pushed that range holds every commit already merged there, so range-scoped rules judged the default branch's commits as the branch's; the pushed range is now the commits reachable from HEAD but from neither `@{push}` nor the default branch's remote ref.
- **What went wrong:** a numbered sub-heading 4.3.2.1 was drafted first, but no leaf uses four-level numbers, so it became a labelled paragraph; the first draft also claimed main merged into the branch was excluded, which a base-to-HEAD diff cannot do, so that case fails closed.
- **Trade-offs:** a stale local default-branch ref only enlarges the range, never shrinks it; the default branch is read from `refs/remotes/origin/HEAD` as in §4.15.7 EC-3, with no new config field.
- **Lessons:** a diff-based range cannot exclude merged-in commits, so any rule that must exclude them falls back to the wider range rather than guessing.
- **Docs:** docs/SPEC/04-03-ENGINE.md
